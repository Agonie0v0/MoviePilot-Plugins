# 115 秒传等待

MoviePilot V2 内置 115 存储的独立插件，当前版本 **0.2.3（测试版）**。

核心行为：视频整理交给独立后台线程。未命中秒传时，MP 原生整理记录显示失败，原因标注等待秒传；后台重试成功并确认远端文件后，调用 MP 原有完成流程，将**同一条记录、同一个 ID** 更新为成功。等待时间通过下次执行时间记录，不占 MP 整理工作线程，也不会在上传函数里长时间休眠。

## 适配范围

- MP **V2.15.6**，源码基准 `jxxghp/MoviePilot@1528176beacc0f9f8d8d9cbf1adf048b0da67b5c`。
- 本地文件 → MP 内置 `u115`，复制或移动整理。
- 视频扩展名可配置，默认覆盖 MKV、MP4、TS、M2TS、ISO 等文件。
- 字幕、NFO、海报继续走 MP 原有流程。
- 蓝光原盘目录暂不支持，返回明确失败，不把目录转为普通上传。
- 第三方存储接管、自定义整理回调和 MP V3 不在当前验证范围内。

自动流程只使用 115 初始化上传及指定区间校验，**不会自动转普通上传**。重试并不保证一定能秒传。点击“强制上传”后，先试秒传，未命中则使用 MP 内置 115 授权及已有的 OSS 库上传文件正文，无需额外授权或生产依赖。

## 安装

推荐在 MP 的第三方插件源中添加 `https://github.com/Agonie0v0/MoviePilot-Plugins`，刷新插件市场后搜索“115秒传等待”并安装。当前标记为测试版，仅适配 V2.15.6；安装后默认关闭，需要手动启用。

也可以使用本地安装包。无需额外安装生产依赖，使用 MP 已有的 Python 库。MP 只加载登记为已安装的插件，单纯复制文件并不能完成安装。

1. 在 MP 页面确认版本是 V2.15.6，内置 115 已授权。
2. 将 ZIP 解压到容器中的临时目录，例如 `/tmp/p115instantwait-package/`，其中应有 `install_local.py` 和 `p115instantwait/`。
3. 在 **MP 自身的 Python 环境及应用根目录** 执行下面的安装命令。脚本复制插件文件，并在 MP 的已安装插件列表中追加 `P115InstantWait`；已有源码会先备份，插件数据目录不覆盖。
4. 重启 MP，在插件管理中查找“115秒传等待”，配置并启用。

```bash
# 在 MP 容器内、应用根目录执行；python 应指向 MP 运行所用的解释器。
PYTHONPATH="$PWD" python /tmp/p115instantwait-package/install_local.py
```

Docker 常见应用路径为 `/app/app/plugins`，应以容器内实际路径为准。临时复制进容器的文件会在重建容器时丢失，长期使用应通过插件仓库或持久化部署安装。

队列保存在 `_PluginBase.get_data_path()` 返回目录下的 `queue.db`，通常为 MP 持久化配置目录中的插件数据目录。备份整个目录时，应停止插件或采用 SQLite 的一致性备份，不要只复制正在写入的数据库主文件。

启用前停用其他会接管 115 上传或整理流程的插件。插件检测到整理接口已被其他补丁替换时会拒绝启用；其他插件若绕过这些接口，仍需要在实机确认不存在冲突。

## 使用

按平时的方式在 MP 发起整理即可。即使文件第一次就能秒传，也先登记后台任务，再由后台执行，避免在 MP 整理线程计算大文件 SHA1 或访问 115。

| 阶段 | MP 整理记录 | 插件队列 |
| --- | --- | --- |
| 已接收 | 失败，原因“等待秒传，将自动重试” | 等待首次执行 |
| 未命中 | 仍为失败，保留原 ID | 等待下次重试 |
| 重试用完、授权异常、源文件变化或达到时限 | 失败，标注暂停原因 | 已暂停，等待手动处理 |
| 点击强制上传 | 仍为失败 | 独立线程先试秒传，未命中就普通上传 |
| 手动上传中断或失败 | 失败，标注原因 | 已暂停，等待再次手动处理 |
| 远端确认且 MP 完成回调提交 | 原记录更新成功 | 整理成功 |
| 人工取消 | 失败，原因“已取消” | 已取消 |

默认首次尝试后最多自动重试 **3 次**，即最多尝试 **4 次**。默认间隔为 60、180、600、1800 秒：默认次数下使用前三个间隔；调高次数后会使用第四个，并在用完间隔列表后沿用最后一个。间隔有 ±10% 偏移，每轮结束后才开始计时。网络等执行错误也计入自动尝试次数。

次数用完或达到等待时限（默认 24 小时），任一条件先满足就暂停。等待时限设为 0 只取消时间限制，仍有次数限制。点击“继续等待秒传”会重置自动次数和等待时限，仍然只试秒传。

升级后已有任务也遵循次数限制；未保存过独立自动计数的旧任务以已有尝试次数为基准，不会因升级自动普通上传。

### 配置怎么填

通常只需打开“启用秒传等待”，其余保持默认后保存。

| 配置 | 含义与默认行为 |
| --- | --- |
| 启用秒传等待 | 接管本地视频到内置 115 的复制/移动整理。默认关闭；打开并保存后生效。 |
| 等待与暂停通知 | 默认开启。每轮首次进入等待及重试耗尽、等待到期、源文件变化、授权异常或手动上传失败时，提交 MP 渠道通知并保留站内系统消息；中间重试和手动暂停不推送。 |
| 每次重试间隔 | 单位为秒，英文逗号分隔。默认 `60,180,600,1800`：依次约等 1、3、10、30 分钟，间隔不足时沿用最后一项，但仍受次数上限限制。每轮结束后计时，含 ±10% 浮动。每项允许 30～86400 秒。 |
| 最多重试 | 默认 `3`，不含首次尝试，共最多尝试 4 次；填 `0` 表示首次未成功就暂停。允许 0～100 的整数。用完后需手动处理，绝不自动普通上传。 |
| 最长等待 | 默认 24 小时，到期暂停并保留文件；填 `0` 表示不限时，但仍受次数限制。继续等待后重新计时。允许 0～8760 小时。 |
| 接管的视频后缀 | 在“视频格式 · 通常无需修改”内。填写后缀，如 `mkv,mp4,iso`，不需要点号；默认包含常见格式，通常不用改。未列出的格式走 MP 原流程，不受本插件的只秒传限制。 |
| 选择任务（可多选、可搜索） | 在“批量任务操作”内。按文件名、状态和整理记录编号搜索并多选，最多 200 项；执行中的任务不可选。 |
| 统一执行 | 强制上传：先试秒传，未命中则普通上传。继续等待秒传：仅对已暂停任务重置次数和时限。暂停：停止排队，之后可恢复。取消：结束任务，保留文件和失败记录。 |
| 保存时对所选任务执行一次 | 插件须启用，选择任务及操作后勾选，再点保存。执行前清空选择并关闭勾选，重启不会重复执行；日常修改设置无需勾选。 |

### 通知渠道

0.2.2 修复了此前只写入站内消息、未调用 MP 通知渠道的问题。需要同时开启插件的“等待与暂停通知”，并在 MP 通知渠道中启用对应消息类型：

- **整理入库**：每轮首次未成功、进入自动等待时推送，包含下次重试时间。后续中间重试不重复推送。
- **手动处理**：次数耗尽、等待到期、授权失效等异常暂停时推送，包含暂停原因和处理入口。若首次执行就暂停（例如最多重试为 0），只发送这一条。
- 整理成功和最终整理失败沿用 MP 原生通知，插件不额外重复发送；上述插件开关不关闭 MP 原生通知。

通知包含文件名、原整理记录编号、累计与本轮尝试次数、原因及任务 ID。日志中的“通知已提交 MP”表示已调用 MP 消息分发流程，不代表客户端已收到，实际接收仍受 MP 渠道、消息类型和用户消息隔离设置影响。“通知提交失败”不会使暂停任务重新运行，也不会中断其他任务。

升级或重启不会补发已暂停任务的旧通知。测试现有暂停任务时，可点“继续等待秒传”，之后的新等待/暂停会按上述规则通知。

### 管理等待任务

点击插件的“查看数据”，展开对应文件，即可点击“强制上传”。无需等到次数用完：等待首次执行、等待重试、已暂停的任务均可手动触发。强制上传不受自动次数和等待时限限制，但仍检查授权、源文件完整性及目标冲突。

配置页“批量任务操作”支持多选后统一强制上传、暂停、继续等待或取消。保存时逐项检查最新状态，已结束、不支持操作或已不存在的任务会跳过；某一项异常不会阻止其他所选任务。重复 ID 只处理一次。批量强制上传依次进入现有手动上传队列，不增加并发数。

重新打开配置页，在“批量任务操作”中查看上次结果，包含已接受、跳过、异常数量及逐项原因；“已接受”只表示命令已提交，不表示文件已上传完成。原整理记录仍在真正完成后才更新成功。日志也保留汇总和每个任务的操作记录。操作请求在执行前消耗，若进程中途退出，不会在重启后自动重放未完成的批量命令；请核对任务状态后重新选择。

也可选择“暂停重试”“继续等待秒传”或“取消等待”。列表中的“已尝试”是累计执行次数（含手动处理）；继续等待只重置当前一轮自动计数，不清空累计数。

任务摘要常驻显示当前状态、累计尝试次数、下次重试时间（MP 所在时区）。本轮自动 `2/4` 表示当前周期已经自动尝试 2 次、最多 4 次，包含首次尝试；累计次数还包含历史周期和手动处理。暂停或插件关闭时不会显示旧的重试时间，改为相应处理提示。页面是打开时的快照，重新打开可更新。

状态使用颜色、图标和文字共同区分；时间与次数加粗显示。展开后优先显示最新结果和操作，源/目标路径及任务 ID 放在“路径与日志定位”中。

### 在 MP 日志中溯源

在 MP 日志页面搜索 `115秒传等待` 查看插件流程；进一步搜索任务 ID，或 `整理记录=2934` 这样的原记录编号，可以串联同一任务的各次尝试。

0.2.1 起记录入队、每次自动/手动执行、等待安排、暂停原因、秒传命中、转普通上传、恢复上传、用户操作、重启恢复及整理结果。普通进展写入 INFO，暂停和整理失败写入 WARNING。日志包含文件名、任务 ID、原整理记录 ID、累计次数、本轮自动次数；等待日志还包含下次重试的绝对时间、时区及实际间隔。

示例（虚构任务，字段节选）：

```text
【115秒传等待】开始自动尝试 | 任务=example | 整理记录=2934 | 文件=Movie.mkv | 已尝试=2 | 本轮自动尝试=2/4
【115秒传等待】等待下次重试 | 任务=example | 整理记录=2934 | 文件=Movie.mkv | 已尝试=2 | 本轮自动尝试=2/4 | 原因=未命中秒传，等待下次重试 | 下次重试=2026-10-04 00:37:06 +0800 | 间隔秒=180
```

日志从升级后的执行开始记录，不会补造过去每次重试的明细；历史保留时间遵循 MP 日志设置。不会输出 Cookie、上传临时密钥或完整接口响应。

手动上传由另一个独立后台线程串行处理，不占用秒传重试线程和 MP 整理线程。排队期间可暂停或取消，执行期间拒绝重复操作；普通上传会使用上行带宽，网络和磁盘资源仍由所有任务共享。

也可以在配置页展开“单个任务操作”按上表操作。正在执行的任务拒绝重复操作，等本轮结束再操作即可。插件关闭时需先启用再操作。也可使用 MP 已认证的插件 API：

```text
GET  /api/v1/plugin/P115InstantWait/tasks
POST /api/v1/plugin/P115InstantWait/tasks/{task_id}/pause
POST /api/v1/plugin/P115InstantWait/tasks/{task_id}/resume
POST /api/v1/plugin/P115InstantWait/tasks/{task_id}/cancel
POST /api/v1/plugin/P115InstantWait/tasks/{task_id}/upload
```

实际 API 前缀以 MP 的插件路由为准。请通过插件操作等待任务，等待期间不要在 MP 手动删除这条整理记录；删除记录后无法保留已被删除的记录 ID。MP 的普通失败通知及 AI 自动重试不会针对“等待秒传”触发。

## 文件与恢复

- 等待期间保留本地源文件；文件大小、修改时间或文件标识变化后暂停，避免复用错误哈希。
- 新文件先进入目标目录下的 `.mp115-staging/{任务ID}/`，远端确认后再进入正式目录。
- MP 要覆盖或清理的旧版本文件，移到 `.mp115-backups/{任务ID}/` 保留；不会直接删除旧版本。这些目录需要用户按保留策略清理，取消的暂存文件也保留。
- 移动模式在远端确认且整理历史提交后沿用 MP 的成功处理，并清理源文件；复制模式保留源文件。下载器种子清理遵循 MP 原有批次判断。
- 队列持久化保存哈希、秒传文件 ID、整理结果、原历史 ID。重启后恢复等待任务，已经得到远端文件 ID 的任务优先核对远端，不重新发起上传。
- 普通上传保存上传会话 ID 和已完成分片的回执，不保存临时上传密钥。上传失败或正在上传时重启会暂停；再次点“强制上传”先核对远端，然后从已保存分片继续。尚未开始的手动上传队列在重启后继续排队。
- 提交结果响应丢失时，复用同一上传会话并核对暂存文件，避免新建重复文件。若 115 已清理上传会话且远端文件始终不可见，需要人工核对，插件不会直接新建另一份上传；取消任务也不会删除已上传的分片或暂存文件。
- 同一批次只在未完成任务结束后触发批次刮削。重启时恢复本插件已完成与未完成的批次成员；同批次中由其他插件或普通本地整理产生的内存汇总，不保证跨重启完整重建。

MP 历史数据库与插件队列不是同一个事务。插件通过任务标记、远端 ID 与结果检查点处理主要中断窗口，但 MP 完成回调包含通知、事件等多个外部副作用，无法保证这些副作用在任意崩溃点都恰好执行一次。若回调已提交成功历史但尚未执行完，恢复时会避免重复发送完成事件，后续通知或种子清理可能需要人工核对。

## 测试

```powershell
python -m pip install -r requirements-dev.txt
$env:MP115_REFERENCE = '你的 MoviePilot V2.15.6 源码目录'
python -m unittest discover -v
python scripts/build.py
```

在 Linux 中使用 `MP115_REFERENCE=/path/to/MoviePilot python -m unittest discover -v`。参考源码应固定到上面的提交，而不是未来变化的 `v2` 分支。

测试从 MP 源码读取实际 `JobManager`、历史模型、记录写入、完成回调、批次处理、`FileManagerModule.transfer` 和 `TransHandler.transfer_media`。包含原生目录规划、Jinja 重命名、覆盖判断及文件转移，隔离下载器、元数据服务、模块分发和网盘，并非完整 MP 服务的端到端测试。未设置 `MP115_REFERENCE` 时，仅运行队列与 HTTP 协议测试，MP 集成测试会跳过。

0.1.1 补充了 115 文件信息对象/数组响应兼容、返回 ID 核对、源文件在哈希前或完成回调前变化的保护，以及秒传已命中但文件 ID 暂不可见时避免重复初始化的恢复逻辑。

0.1.2 重做配置页和任务详情，使用 MP 原生 Vuetify 组件适配窄屏及主题。常用设置直接显示，文件范围和单任务操作折叠；新增逐项说明、按文件名选择任务及详情页操作按钮。UI 通过本地示例队列渲染检查，尚未在真实 MP 容器中验收。

0.2.0 新增限次自动重试和手动强制上传。测试覆盖次数用完后暂停、手动秒传命中不上传正文、未命中后普通上传、原记录回写、分片恢复、提交响应丢失、源文件变化保护，以及上传期间其他任务继续执行。115/OSS 响应由测试模拟，并非真实账号联调。

0.2.1 增加关联原整理记录的全过程日志，重排任务页的信息层级，突出状态、次数和时间，并校验暂停/关闭状态下的时间显示。用户已反馈实机任务列表与成功记录；本次新日志和样式在本地测试及示例页面验证，未直接连接用户容器。

实机首次验收建议使用独立测试目录和复制模式，核对：

1. 未命中时记录失败，源文件存在，其他文件继续整理。
2. 重试成功后原记录 ID 不变、目标文件可访问。
3. MP 重启后仍继续等待，无重复记录、重复网盘文件。
4. 复制模式通过后，再验证移动模式与覆盖模式。

目前没有连接真实 115 账号或用户的 MP 容器。源码测试通过不等于实机验证完成。
